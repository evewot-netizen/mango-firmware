# Controlled Mango updates (staged development)

The intended Pi policy is a nightly check at 04:15 local Home Assistant time.
No update means no backup. A newer approved, signed image must pass preparation,
then the Pi must create and verify a backup before submitting installation.
Retain three successful backups. No HA scheduler is installed here yet.

## Router setup stages

1. `install-router-prepare.sh`: historical first installer, replaces the tested
   procd selftest with background preparation only.
2. `install-router-control.sh`: backs up and extends that setup with an install
   worker. It requires that no install worker/activation flag already exists
   and no job is active. **It does not activate installation or start a job.**

Both installers preserve helper files via sysupgrade.conf, disable service boot
startup and configure no respawn. The second installer is generated by
`python3 management/build_installer.py` from the current router sources.

The forced-command key accepts `status`, legacy synchronous `check`, background
`prepare`, and `job`. The gated `install IMAGE_SHA256 BACKUP_SHA256` command only
accepts two lowercase 64-character hashes. It requires the root-owned activation
file `/etc/mango-ha-update-install-enabled` to contain exactly `enabled`. This
file is deliberately neither created nor added to sysupgrade.conf here.

## Preparation and installation

The native autoupdater validates manifest signatures, model, version and image
hash. A downloaded image is moved into a private temporary directory, recording
its SHA256, preparation time and old release. READY work is retained. Errors and
ambiguous output fail closed; unrelated /tmp/firmware.bin is not overwritten.
Parser messages match freifunk-gluon/packages commit
`d75722c2ee89dcca228b02465bdd8107c574676d`.

The install worker rechecks activation, state, both hashes, the staged image,
the unchanged installed release, and a maximum preparation age of one hour.
It locks out the native updater and uses strict `sysupgrade --test` without
force or compatibility overrides. It records an audit receipt, runs download
and upgrade hooks, then hands that exact staged image to sysupgrade with normal
configuration preservation. Hook failures before handoff run abort hooks.
The procd worker is independent of the initiating SSH connection.

**The backup hash is an audit reference, not proof that a remote archive exists.**
The Pi-side controller must verify the backup before invoking installation.
There is no automatic rollback guarantee after flash begins. The normal Gluon
hooks deliberately stop networking before sysupgrade. This phase has only been
mock-tested; no real flash has been validated.

Still required: hardware validation of the Pi flow, firewall-specific postflight
checks, notifications, sequential multi-router handling, and activation of the
complete HA schedule. No unattended rollout is enabled.

Tests: `python3 -m unittest discover -s management/tests -v`.

## Pi controller (not yet scheduled/activated)

`install-pi-control.sh` installs the standard-library Python controller, a local
configuration and three HA shell commands: `mango_update_start`,
`mango_update_schritt`, `mango_update_status`. It checks HA configuration and
creates no automation. `installation_enabled` is false. The router activation
flag also remains absent. The controller executes inside HA Core, not core-ssh.

Each invocation performs at most one bounded step. Persistent state and a file
lock prevent overlapping controllers; the INSTALLING state is committed before
sending the install request, so a lost acknowledgement never triggers a repeat.
After reboot it checks the expected release, changed boot ID, WireGuard SSH,
Freifunk VPN and mesh twice. Router firewall-specific postflight checks and
schedule/notifications/activation still need completion before unattended use.

The controller fetches release metadata over HTTPS and requires the image hash
to match the router's signed-manifest-verified candidate. A changed channel
fails closed. Backup downloads are bounded to 30 seconds/16 MiB, archive contents
to 32 MiB, and required files include all new update helpers. Backups are verified
again before installation; only the latest three successful archives are kept,
ordered by filesystem modification time (not timezone-dependent filenames).
The backup SHA is passed together with the exact image SHA. Missing or changed
backups, changed candidates, wrong post-reboot versions and timeouts stop the
flow. ERROR and uncertain installation never automatically restart a rollout.
